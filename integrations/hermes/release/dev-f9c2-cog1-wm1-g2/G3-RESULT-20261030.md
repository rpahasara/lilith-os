## Why the reply used the id (offline analysis)

Method: the exact prompt text, rebuilt offline from the real Core API and grounding code on a throwaway DB (`exposure_exact.py` in the
package), plus the recorded reply. No private session was read and no provider was called.

| Finding | Evidence |
|---|---|
| The title was available | Both goal lines and the `CURRENT FOCUS` line carried it |
| The id comes first | Goal lines read `GOAL <id>: <title>`, and the focus line reads `<id> - <title>` |
| Nothing says which to use | The policy says to report the current focus. It never mentions titles or ids |
| The question asks for a selection | `which goal has priority?` is answered fully by a short handle, and the reply was 42 completion tokens |

**Conclusion:** the prompt leaves the choice to the model, and the id is the first handle. That is the likely cause, not a proven one:
one reply cannot show how often this happens. No code was wrong. The criterion assumed something the prompt never asked for.

**Possible fix, not made:** add a policy rule such as "name a goal by its title; give its id only if asked". It changes provider-bound text, so it needs a
release and a live check.

## A defect G3 would not have found

The offline negative control for a populated store found a real over-match. It is outside the G3 scope, and its result does not change this record.

The deployed `detect_goal_intent` matches casual uses of the word: `my goal for the weekend is to relax`, `nice goal last night`,
`who scored that goal?`. With Goals live and a populated store, a real-gateway test shows such a message makes both goal reads, writes 1 `goal_trace` row and adds
every goal title to the provider-bound prompt.

The planned L2 message, `hey how are you`, does not contain the word and would have passed. **DEV is not exposed:** r1 has Goals in shadow and 0 goal rows.
This must be fixed before real goals or another Goals Live window.
