# Slice 15B2b — Trusted broker-only DEV validation path

Status: governance control, not Stage-III authorization. This change does not implement the A2 fault seam or install a broker candidate.

## Change scope determines validation scope

The protected-main `scripts/classify_dev_deployment.py` classifies the complete effective base-to-candidate diff. It accepts ordinary added/modified files only; deletion, rename, symlink, submodule, unknown path, or mixed classes select `DEPLOY_REQUIRED`. The existing exact Stage-II control set remains `CONTROL_ONLY_NO_DEPLOY` and retains its pinned installer blob and CI-step checks. A closed broker-owned set selects `BROKER_CANDIDATE_VALIDATE_ONLY`: the nine broker package files named by `BROKER_CANDIDATE_PATHS`, four dedicated broker tests, the owner-request golden fixture, and one future A2 architecture record. No directory wildcard is used. Core API files, the shared owner-proof verifier and other shared dependencies, deployment/build/installer/control scripts, workflows, units, dependency declarations, and unknown paths are excluded. A broker-plus-any-excluded-path diff therefore takes the full route. Neither candidate metadata nor an input or environment variable can choose a narrower mode. A change to this classifier or workflow cannot classify itself under the new lane.

Previously, every change outside the Stage-II control-only set selected `DEPLOY_REQUIRED`. That branch builds an exact-SHA API bundle and invokes `deploy_core_api_dev_remote.sh`; the script restarts the DEV API before the workflow's transient broker validator runs. A broker-only change thus caused an unrelated API restart. The existing `memory_broker_validation.py` builds an exact-SHA broker artifact, verifies its manifest and file hashes, extracts it into a temporary directory, runs synthetic broker and shared-owner-proof tests, then removes the temporary directory. The existing DEV runner compares accepted lifecycle snapshots around that execution. The DEV SSH account can invoke privileged Python, so untrusted candidate execution on that VM is not an acceptable isolation boundary for the new lane.

## New required-check route

The same `LILITH DEV deployment` commit-status context remains required. The initial job uses protected-main controls and the exact CI-validated candidate SHA, publishes pending, and routes only a closed broker diff to three separate hosted jobs:

1. A credentialed preflight job checks the pinned DEV project, zone, instance name and ID, then uploads only trusted lifecycle source to a bounded `/tmp` directory. It runs the accepted lifecycle snapshot read-only, removes that source, and requires `POST_STAGE_II_ACCEPTED_V1`, digest `abc33ebf8d43e8805f43ff11e663a4757bf558d9b62eda9669dabecbb7c9839a`, installed release `817a83e44cec8965479fd97fc30b7a0b3ae49ab2`, broker PID 96650, API PID 88740, active/listening broker, healthy API, and valid process boot/start identities. The existing lifecycle validator also pins machine identity, files and unit custody, owner/evidence rows, sidecars, used authorizations, and the accepted invocation. It produces a SHA-256 of the *complete* snapshot.
2. A fresh, credential-free hosted runner builds the exact candidate broker validation artifact and inert release using protected-main builders, verifies both, and executes the existing transient validator against synthetic fixtures in a temporary directory. The artifact attestation records source, archive and per-file hashes; the release attestation/manifest records source, archive, manifest, payload and dependency hashes. No candidate archive or executable is sent to DEV; there is no GCP authentication, live owner socket, database, canonical memory, installed broker release, or runtime service in this job.
3. A separate credentialed postflight job re-reads the accepted DEV lifecycle using protected-main code and requires exact complete-snapshot equality with preflight. This includes unchanged API and broker PIDs, boot/start identities, NRestarts, unit/app/custody hashes, socket state, owner and evidence row hashes/counts, and authorization history. It audits the pinned PROD VM read-only for continued darkness. Only all successful stages publish success to the original required context; failure publishes failure.

The broker-only branch cannot invoke the Core API deploy script, restart either service, switch broker `current`, install the candidate, create owner authorization/evidence, or mutate an accepted database. Its only DEV staging is the trusted read-only lifecycle script; cleanup is restricted to that temporary file and directory. Candidate test fixture cleanup happens on the hosted runner. Any changed accepted state fails the gate. The original full-deploy and control-only routes are unchanged.

The first A2 required-check run failed in trusted DEV preflight after `mktemp` created an empty directory: the old helper treated the complete `gcloud compute ssh` stdout as the path and rejected it with `REMOTE_STAGING_PATH` before entering its cleanup block. The original stdout bytes were not retained, so transport-output contamination is the evidenced failure class, not a claim about a particular banner. No candidate artifact was built or executed. The empty directory was verified and removed separately.

Protected-main workflow context now supplies numeric GitHub run ID and attempt to the trusted snapshot helper. The helper, not SSH output or candidate data, derives separate exact paths `/tmp/lilith-broker-candidate-preflight-<run-id>-<attempt>` and `/tmp/lilith-broker-candidate-postflight-<run-id>-<attempt>`. It pins the DEV instance name/ID before creation. Only the trusted lifecycle source (mode 0600 after upload) and its read-only snapshot result (mode 0600) may appear there. The helper retrieves the result as a file and never interprets SSH stdout as a staging path or snapshot. Cleanup validates the exact run-bound path, directory custody, and known file set before unlinking those two files and removing the empty directory. Unexpected contents are preserved and reported; uncertain creation or cleanup reports the exact path for audit. Nothing is staged on PROD, and the hosted candidate job remains credential-free.

## Trusted SSH stream transport refinement

Historical record: the SSH-stdin method below was merged in PR #40 but failed its first normal Linux preflight in run `35986496264`: after 120 seconds, `lifecycle.py.part` was still zero bytes. Cleanup succeeded and accepted DEV did not change. The exact Linux cause is **unproven**. The packed command-channel refinement below supersedes stdin upload for this one trusted helper.

The first two normal A2 validation attempts after the path repair both timed out after 120 seconds in `gcloud compute scp` while uploading the 66,984-byte trusted lifecycle source. The run-bound destination file was observed at zero bytes with SFTP active; the exact cause of the stall was not established. Both attempts cleaned their staging directories, and the hosted candidate job skipped. The broker-only lane therefore replaces **only this trusted source/result transfer**, not general deployment transport, with authenticated `gcloud compute ssh` over IAP and non-TTY stdin streaming.

Protected-main code reads the fixed lifecycle file, bounds its byte length, and computes SHA-256 before opening the remote staging directory. The fixed-purpose remote writer exclusively creates `lifecycle.py.part` at mode 0600 inside the validated directory, streams raw stdin bytes without shell interpolation, fsyncs, checks exact byte count, SHA-256, regular-file custody and single link, then atomically renames it to `lifecycle.py` and fsyncs the directory. A short stream, extra byte, wrong hash, pre-existing file, or transport error never publishes the final source. The fixed interpreter executes only a revalidated final file. The snapshot is written to a separate bounded mode-0600 file. A read action returns one size/hash-checked, base64-framed payload over SSH stdout; transport chatter is never accepted as path or lifecycle JSON. The same mechanism serves preflight and postflight. Cleanup uses explicit empty, partial, or published states: each accepts only its expected trusted files, verifies custody, and preserves unexpected contents for audit rather than mistaking a pre-existing final file for this run's publication. Candidate bytes remain solely on the credential-free hosted runner.

## Packed protected-main command-channel transport

Only the fixed protected-main `verify_broker_dev_lifecycle.py` adjacent to the trusted snapshot helper is eligible for transfer. The broker candidate checkout cannot select or supply the validator. The workflow pins the protected-main base checkout for both credentialed phases and keeps candidate build/tests in a separate credential-free hosted job. The pinned DEV instance name and numeric ID are checked before staging. PROD is never a packed-payload destination.

The trusted runner rejects an absent, symlinked, empty, or oversized lifecycle source; computes its raw size and SHA-256; compresses it deterministically with zlib level 9; and URL-safe-base64 encodes it. The current reviewed source is 66,984 bytes with SHA-256 `ba558b293e6ceba30fc3a3d373731ac05f83396a4e4bf58c3bc0bb4d6e95da9b`, compressing to 17,874 bytes and encoding to 23,832 ASCII characters. The packed payload is one bounded argument to the fixed `gcloud compute ssh --tunnel-through-iap --command` invocation, **not** SCP/SFTP or remote stdin. The fixed decoder itself is protected-main code, compressed into the command to keep the complete command comfortably below Linux's per-argument bound; neither candidate text nor candidate paths enter it. Raw, compressed, encoded, and complete command lengths are bounded locally, and successful transport logs only those lengths, the raw hash, action, and result—not the payload.

The remote fixed-purpose decoder validates URL-safe base64, exact compressed length, zlib termination with no trailing data, bounded decompression to at most expected raw size plus one byte, exact raw size, and SHA-256 **before** creating a file. It then validates the run-bound mode-0700 directory, exclusively opens `lifecycle.py.part` mode 0600 without following a symlink, writes and fsyncs the trusted bytes, re-reads size/hash/custody/link count, atomically renames to `lifecycle.py`, rechecks the final file, and fsyncs the directory. Only after a single bounded publish-result frame is validated may the fixed snapshot invocation run. Snapshot JSON remains a separate mode-0600 file returned through its existing size/hash-checked frame; transport chatter is not semantic output. Both preflight and postflight use this identical path. No fallback to stdin or SCP is permitted.

Cleanup accepts only the exact run-bound directory and recognized partial/published files. Explicit unexpected-content failures preserve that content; an uncertain publish may clean an owned partial file or a final file only if the final content matches the trusted source hash and size. Unknown files, wrong custody, or a mismatching final file are preserved and reported. The full API deployment route and its SCP behavior are unchanged. This governance repair cannot certify itself: the previous protected-main classifier selects full deployment for its helper/workflow diff, so any forbidden API-restart bootstrap must follow a separately reviewed exact-head owner exception. The A2 candidate PR still requires all four ordinary checks and must not be merged by this transport change.

The one authorized feasibility probe used 19,000 deterministic non-executable bytes (SHA-256 `bb9b076645c0f7718a59253825f19918dc39dcbd3ff3b8c9477e50cdf69588a1`), 19,016 compressed bytes, 25,356 encoded characters, and a 28,448-byte complete remote command. It published through the actual DEV IAP/SSH command path in 11.809 seconds and cleaned the exact run-bound file and directory. The preceding and following read-only accepted snapshots both had digest `6cc57ff3729d88c869b4a137e73ad3bd47c3719d11d0de99769355a0edf20d27`; API PID 88740 and NRestarts 0, broker PID 96650 and invocation, database hashes, 24/24/2/2 history, and staging-residue scan were unchanged. This proves command-channel feasibility for that bounded payload, not an underlying cause for the earlier SCP or stdin failures. The DEV host reported `ARG_MAX=2097152`, `PAGE_SIZE=4096`, and `MAX_ARG_STRLEN=(PAGE_SIZE * 32)` in its kernel header. The helper's 26,922-byte lifecycle publish command is far below that per-argument cap; the workflow also logs exact Cloud SDK, SSH, Python, runner OS, and argument-limit versions/values for subsequent validation.
