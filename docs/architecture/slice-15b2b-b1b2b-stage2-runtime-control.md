# Slice 15B2b-B1b-2b Stage-II runtime control: API baseline repair

## Research record

**STAGE-II CONTROL MODEL DEFECT — VOLATILE DEV API PROCESS IDENTITY WAS INCORRECTLY ENCODED AS A DURABLE SOURCE-CONTROL INVARIANT.** The original trusted Stage-II source required Core API PID `80100` and its September 23 start time. A separately owner-authorized bootstrap restart legitimately changed that process identity while the service remained healthy and its trusted configuration and custody were unchanged. Read-only Stage-II preflight therefore stopped before authorization or activation. This was a control-model defect, not an API deployment defect.

The correction pins durable DEV API identity and custody in trusted source, then captures volatile process identity for each future authorization. It does not pin replacement PID `88740` or its start time in source. The old and new identities are test fixtures only.

## Durable and observed boundaries

The pinned DEV host check still requires exact GCE project, zone, instance ID/name, local FQDN, and machine ID, and explicitly rejects PROD. Stage-I release, identities, configuration, database custody, and inert broker/socket checks remain unchanged. API service name, loaded/active/running state, `lilith` user/group, exact working directory, fragment path, absence of drop-ins, executable and command line, app SHA-256, API unit SHA-256, canonical-runtime and legacy DEV DB SHA-256, `NRestarts=0`, and healthy `/health` result are durable acceptance conditions. PID must be positive and start time present, but neither value is source-pinned. The exact unit hash also anchors the on-disk service command and configuration.

`ApiRuntimeBaselineV1` is a closed record with `schemaVersion=1`, service name, `MainPID`, `ExecMainStartTimestamp`, `NRestarts`, active/substate, service user/group, working directory, observed `ExecStart`, app and unit SHA-256, health result, custody hashes, and UTC capture timestamp. Its digest is SHA-256 of UTF-8 JSON with sorted keys and compact separators, matching the existing marker serialization convention. `ExecStart` includes the process start and PID as observed by systemd, so session drift is also visible there.

The Stage-II authorization marker is now a closed schema version 2 record. It contains the full trusted API baseline and `apiBaselineDigest`; schema version 1 is rejected. Before the single-use marker is consumed or any activation mutation, the control reruns the complete inert Stage-I/API preflight and immediately re-observes the API against the marker-bound baseline. It does not silently recapture or replace authorization when PID, start time, restart count, health, command, binary, unit, or custody changes. After the Stage-II experiment, it compares the complete API observation again using the authorized capture timestamp. Any drift is an API non-interference failure; existing failure containment stops broker and socket and preserves evidence.

This control-only repair grants no activation. The prior owner activation decision is not carried forward. After a protected merge and read-only preflight, a fresh owner decision is required before Stage-II marker creation or runtime mutation. No Stage-III, PROD, IAM, real-credential, live-authority, or real-memory capability is introduced.

## Retry #2 control repair after failed-inert run 35924789001

The V1 API baseline above remains the historical meaning of the consumed attempt-#1 marker; it is not reinterpreted. Its raw `ExecStart` string contained systemd runtime annotations (`pid=` and `start_time=`). A daemon-reload on the failed run changed those display annotations to `pid=0` and `start_time=[n/a]` while the actual API PID 88740, process start, restart count, app/unit/custody hashes, and health did not change. Comparing the entire string incorrectly reported an API restart.

`ApiRuntimeBaselineV2` (`schemaVersion=2`) separates configured identity from incarnation. Configured identity includes the exact service, host/machine, user/group, working directory, normalized `ExecStart` executable and arguments, app/unit SHA-256, and custody hashes. `ExecStart`'s runtime annotations are parsed only as display context and excluded from its digest. Incarnation includes `MainPID`, systemd's actual `ExecMainStartTimestamp`, `NRestarts`, active/substate, Linux boot ID plus `/proc/<pid>/stat` start ticks, the actual executable and complete command line, and health. A future marker captures the complete V2 record and digest. Immediate pre-consumption and post-experiment observations compare this complete security-relevant record with a fixed capture timestamp. PID, kernel start ticks, restart count, configured command, executable/cmdline, host, health, app, unit, or custody drift fails closed; a bookkeeping-only daemon-reload does not.

The new closed Stage-II marker is schema version 3. It requires V2 API identity and binds a `Stage2RetryBaselineV1` digest. Schema-2/V1 markers cannot be used under V2 semantics. The original used marker remains terminal and byte-for-byte pinned at `b1b2b-stage2-authorization.used.json`; retry #2 would consume its distinct marker into `b1b2b-stage2-retry2-authorization.used.json`. A new authorization ID must differ from `4006ead71ca04c219b3b41e6818010f2`. This control PR creates no marker and performs no retry.

`Stage2RetryBaselineV1` admits only exact `POST_STAGE_II_FAILED_INERT_V1` history. Its pinned input is historical digest `8068e066743d70252a6fd0f0e6fdbab12c1be2c9ac00e152c4746ee810fcfe83`, two exact DB file hashes and sidecar hashes, schema fingerprints, the old used marker hash/authorization, 12 challenge IDs/states, 12 request IDs/digests, one claim, and the existing `se.68b647fc14aeea4fb32bdd7d0fada54d8f4af7c272ec6784f5d22c4c8980e7b5` evidence. Complete historical row hashes include opaque payloads and timestamps without disclosing them. Static rows and SQL schemas are also fingerprinted. The baseline records the inactive broker/socket and empty root:ipc `0710` runtime directory; it is evidence, not activation authority. Trusted preflight and an immediate pre-consumption recheck compare its digest before the first mutation.

A future retry tests exactly 12 *new* challenge/request pairs: one consumed successful confirmation, ten cancelled, and one expired. Its one new claim and `se.*` evidence must link to that success and agree on challenge and request/action digests. Replay, cancel, expiry, invalid assertions, and binding mismatches add no evidence. End state is historical 12/12/1/1 plus new 12/12/1/1, never a zero-history assumption. Every historical row hash, static row, SQL schema, and old used marker must remain exact; any unexplained new row or old-row edit/relink fails. Reports label attempt-#1 evidence separately from retry evidence. Failure containment preserves both attempts' terminal history; no deletion, rollback, or reuse of the old authorization occurs.

The prior IPC sequence ran relay HEALTH before the first negative peer probes. The repaired sequence creates the runtime directory, starts only the socket, verifies the service is still inactive, probes `lilith` and unrelated `nobody` for filesystem/socket denial, verifies inactivity again, then uses relay HEALTH for legitimate activation. Afterward it observes actual `SO_PEERCRED`, probes the broker UID as a client, and retains forged-message identity rejection. Directory/socket denial is valid Layer-1 isolation; permissions are not loosened to force Layer-2 reachability. The dedicated test records call order and fails if HEALTH precedes either negative probe.

This is a control-only repair. No DEV deployment, Stage-II dispatch, marker creation, daemon-reload, service activation, synthetic proof traffic, PROD/IAM change, or real-memory capability is authorized by the repair itself. A protected merge and read-only readiness check still stop for fresh owner authorization of `B1B2B_II / ACTIVATE_AND_ISOLATION_TEST — RETRY #2`.
